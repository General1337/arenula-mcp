# FrameBasisAnalyzer

Roslyn analyzer for the gravity-hull subsystem. Enforces the frame-tagged vector
type system declared in `Code/SBEP/Ship/GravityHull/Math/FrameTypes.cs`
(`WorldVec3`, `ShipLocalVec3`, `HullFrameVec3`, `Vector3Extent`).

## Diagnostics

| ID | Severity | Triggers on |
|----|----------|-------------|
| FBA001 | Warning | `Vector3`-typed local / parameter / field / property declarations inside the scanned paths. Fix by picking one of the four frame types. |
| FBA002 | Warning | Cross-frame arithmetic — addition, subtraction, or method invocation mixing two distinct frame-tagged types. Convert through a `GravityHullVolume` first. |

`FBA002` fires anywhere a frame-tagged type appears (even outside the scanned paths)
because cross-frame mixing is always wrong. `FBA001` is path-filtered to the
gravity-hull subsystem so the rest of the codebase is not flooded with warnings
while the mechanical refactor is in progress.

Severity is **Warning** in Phase 2 (R5 — gravity-hull-instrumentation-suite) so
the mechanical refactor can land file-by-file without breaking the build. Phase 4
promotes both rules to **Error**.

## Scanned paths (FBA001 only)

- `Code/SBEP/Ship/GravityHull/**/*.cs`
- `Code/SBEP/Tests/GravityHull/**/*.cs`
- `Code/SBEP/Debug/StepDebugger*.cs`
- `Code/SBEP/Debug/GravityHullDebugOverlay.cs`

The path filter looks at `SyntaxTree.FilePath` so it works regardless of whether
the file is compiled by the engine compiler or by `dotnet build`.

## Build + ship the DLL

`dist/` (not `bin/`) is used so the gitignore `bin/` rule does not exclude the
DLL from commits. The build outputs land in `bin/Release/netstandard2.0/`; copy
the DLL into `dist/` after a successful build:

```bash
dotnet build Libraries/arenula_mcp/Editor/Analyzers/FrameBasisAnalyzer -c Release
cp Libraries/arenula_mcp/Editor/Analyzers/FrameBasisAnalyzer/bin/Release/netstandard2.0/FrameBasisAnalyzer.dll \
   Libraries/arenula_mcp/Editor/Analyzers/FrameBasisAnalyzer/dist/
git add Libraries/arenula_mcp/Editor/Analyzers/FrameBasisAnalyzer/dist/FrameBasisAnalyzer.dll
```

## Wire the analyzer into your local `arenula_mcp.editor.csproj`

**Manual step — `*.csproj` is globally gitignored in this repo** (see
`.gitignore:8`). The `arenula_mcp.editor.csproj` file is a developer-local
artifact regenerated by the engine; every developer who wants IDE-time
FBA001/FBA002 diagnostics adds the line below to their local copy themselves.
The committed FrameBasisAnalyzer.csproj + dist/FrameBasisAnalyzer.dll are
sufficient for command-line `dotnet build` of the analyzer; this step adds
IDE-time enforcement when arenula_mcp.editor is open in Visual Studio / Rider.

Add inside the existing `<ItemGroup>` containing the `Sandbox.CodeUpgrader.dll`
and `Sandbox.Generator.dll` analyzers:

```xml
<Analyzer Include="Analyzers/FrameBasisAnalyzer/dist/FrameBasisAnalyzer.dll" />
```

## Where the analyzer fires

The analyzer is attached to `arenula_mcp.editor.csproj` only. The engine's
runtime hot-compile pipeline does NOT run analyzers — confirmed by `grep
WithAnalyzers / DiagnosticAnalyzer / AnalyzerReference` returning zero matches
across `S&Box-Pub/engine/Sandbox.Compiling/**`. Diagnostics surface at:

- **IDE edit time** when arenula_mcp.editor is in the open solution (VS / Rider).
- **`dotnet build` time** when building arenula_mcp.editor.csproj directly.

For game-side gravity-hull files (1155 `Vector3` occurrences across 13 files in
`Code/SBEP/Ship/GravityHull/`), the analyzer's catalog signal is currently only
available via direct grep — wiring the analyzer into the game-side compile is
deferred to a future phase that touches the engine-fork compiler. See
`docs/ai/sessions/2026-05-24-gh-r5-frame-basis-strong-types/phase-01-findings.md`
§3 for the engine-side investigation.
